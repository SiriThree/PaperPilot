# 成员 A 性能基线（2026-10-27）

本文记录正式 PostgreSQL 16 数据层在合成数据规模下的首次性能基线实验：方法、数据、结果与结论。机器可读结果见 [performance-baseline.json](performance-baseline.json)，可由 `scripts/benchmark_postgres.py` 在一次性数据库中复跑（结束后自动删除，不触碰业务库）。

## 方法

- 每个场景先建一次性库并迁移，再以单事务 + COPY 播种一致数据（全部延迟约束触发器在提交时通过），`ANALYZE` 后计时。
- 每个场景 33 次执行（3 次预热），报告中位数的 A/B 对比：先测当前索引集合，再建数据字典 §7 的三个候选索引并重测。
- 关键场景附带 `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)` 计划证据（含索引名）。
- **噪声基准**：纯主键查询 `role_check` 的 p50 即客户端+驱动往返底噪；与其同幅度的"提升/退化"一律视为抖动，不作为结论依据。

## 数据规模（单机合成）

200 项目、4 000 论文与项目关联、32 000 片段、5 300 任务（含 4 000 成功 process、1 000 证据、300 待领取 answer）、5 000 执行尝试与结果、200 报告 × 6 版本、100 000 审计事件（集中于单个项目，取最坏密度）、14 000 outbox 行（12 000 待投递）。播种 25.4 秒。

## 结果（两次独立运行一致）

| 场景 | 服务端执行 | 说明 |
| --- | --- | --- |
| 用户项目列表 / 角色检查 / 论文年份过滤 / 来源读取 / 报告最新版 / 缺证据统计 / outbox 领取 | **≤ 0.2 ms**（EXPLAIN 实测） | 客户端观测 1.3–3.3 ms 全部是往返底噪 |
| 任务领取（pending + 过期租约分支，FOR UPDATE SKIP LOCKED） | 毫秒级 | 领取索引 `pending_task_claim` 已覆盖 |
| 审计首页（action 过滤 + LIMIT 20） | 毫秒级 | `project_audit_page` 已覆盖 |
| **审计深分页（OFFSET 20000）** | **≈ 14 ms** | OFFSET 需线性跳过全部被跳过的索引项，属于算法成本 |

## 结论

1. **三个候选索引均未产生计划级收益，本轮不落地**（没有创建迁移 002）：
   - `project_members_user`：1 600 行成员表上规划器在建索引后仍选择 Seq Scan（0.12 ms），无收益；
   - `papers_project_year`：论文路径已按 metadata 主键点查（0.056 ms，Index Scan），无关年份聚合压力；
   - `audit_project_action_time`：深度分页瓶颈在 OFFSET 本身，计划仍为既有索引的 Bitmap Scan，复合索引不改变量级。
   这与数据字典 §7 "候选索引须按实测决定" 的约定一致；写入开销（project_members 是成员变更热表）当前没有对应收益支撑。
2. **审计深分页的正确修法是游标（keyset）分页**，不是索引：AB-1 已声明 "offset 在并发插入时不保证跨页快照一致，若需要游标另行升级"。在审计分页成为产品需求前，保持现状并在该文档中跟踪。
3. **重启评估条件**（出现其一即复跑本基准）：单库成员关系达到 10⁴ 量级；单项目审计事件达到 10⁵ 且存在高频 action 过滤读取；论文/片段量达到 10⁵ 量级；或 B 上报任何接口延迟问题。

## 边界

本机开发笔记本、单一数据形态、无并发负载与真实网络：这些数字用于**索引决策的相对 A/B 证据**，不构成生产容量或 SLA 承诺。并发正确性证据由共享契约测试的真实数据库门槛覆盖（并发导入、并发版本、并发领取、租约恢复），性能联合验收按交接文档仍需与团队共同进行。
